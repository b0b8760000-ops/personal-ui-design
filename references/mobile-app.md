# 手機 App／小程式介面

## 先分開設計目標與實作形式

手機 App 的產品需求可以先規劃；進入具體實作前，依專案確認 Android、iOS、跨平台框架、小程式、行動網頁或其他形式。已有框架時沿用，不替使用者任意換棧。

手機畫框、直向畫面或可點擊預覽不能確認原生實作。React／Vite 是網頁前端線索，不能據此說 Android 原生 App 已完成；也不能只憑這兩個名稱斷定一定沒有原生包裝或其他專案。需要原始專案、建置與裝置證據再判斷。

小程式單獨標示平台與限制，不自動等同一般網頁或原生 App。平台不明但不妨礙設計時，先做產品與互動規劃，不編造 API、尺寸單位或裝置驗證結果。

## 產品與頁面規劃

從主要任務建立頁面／流程，分清主要導覽、細節頁、返回及中斷後恢復。首頁、行程、地圖、我的只是第四支旅行案例，不能作為所有 App 的必備頁面。

跨頁統一字體層級、配色用途、圖片比例、卡片與元件狀態。需要可編輯稿時保留畫板、文字、圖層、元件與變數；先檢查設計資料，再確認程式引用一致。

互動設計讀 [共用方法](common.md) 的十種模式。它們源自手機案例但可跨平台參考；原生平台不能直接以 CSS 方法作為實作方案。觸控拖曳與捲動衝突、可取消操作、精準輸入及減少動態按任務處理。

需要更完整的 App 流程與視覺打磨時讀 [整體規劃與視覺優化](planning-and-visual.md)；需要素材時讀 [背景與素材](backgrounds.md)；需要即時互動時讀 [動畫與互動](motion.md)。這些模組依需求讀取，不要求每次全部執行。

## 設計到開發交接

第四支示範「產品需求／UI 規範 → 可編輯稿 → MCP／D2C → Agent 開發」。這是候選交接方法，不強制採用 Pixso 或任何特定工具。

Figma、框架專用 Skill、Rive／Lottie 與其他工具的選用見 [工具選用與來源](tools-and-sources.md)。先確認當下能力；本 Skill 不依賴這些工具才能運作。

需要時確認：

- 目標設計檔／圖層、素材、元件／變數與程式的對應。
- 目標框架與既有元件，哪些是展示資料、哪些是真實服務。
- 工具實際公開的讀寫與匯出能力、檔案權限、連線與方案條件。
- 生成碼能否取得、依賴能否安裝、建置／執行是否成功。

Pixso D2C、D2C⁺、MCP 與其他功能有不同能力或使用條件，使用時查當下官方文件；不要從演示推論零成本或可直接生成完整 App。[Pixso D2C⁺](https://pixso.cn/developer/zh/d2c/quick-start.html)

下載或安裝受限時，記錄實際錯誤與影響；在可用範圍內繼續，不繞過權限或把部分視覺近似描述為完整還原。原影片的限制不預設會在使用者環境重現。

## 按目標選驗收

以下是檢查方向，並非對特定 OS API 行為的保證；具體實作需查目標平台官方文件。

| 項目 | 檢查方向 |
|---|---|
| 導覽與觸控 | 返回、頁面狀態、點按／拖曳、連續操作與取消 |
| 螢幕與輸入 | 螢幕尺寸／方向、系統欄、鍵盤遮擋、長文字與系統字體 |
| 可及性與動態 | 輔助技術、焦點、可讀狀態與減少動態 |
| 資料 | 載入、離線或失敗、保存、同步、過期與恢復 |
| 裝置能力 | 只有需求涉及通知、定位、相機或背景工作時，才處理相關權限與行為 |
| 交付 | 目標若為可安裝 App，需另外確認建置、安裝與目標裝置操作；網頁預覽不能代替 |

回報清楚區分「介面設計」「互動原型」「成功執行」「真實服務」「可安裝版本」「實機驗證」。缺少證據時提供符合已知範圍的成果說明，不為展示期限提高完成程度。
